# Original compositor to installed native Messages

The isolated trusted fixture now composes actual original Hyprland with the
current Rust observer/lifecycle actor, its real Messages storage worker, and an
installed distinct-UID Qt app. Six normal production-app groups and three separate
10-group diagnostic source epochs pass under the actual ARM guest kernel. The
normal app uses its unchanged production ELF and six standard arguments. This is
local synthetic seeded history, not modem receive, delivery or production session
provisioning. [Authored provenance](evidence/native-session-installed-app-provenance.json)
keeps the evidence classes and failures separate.

The launcher owns the actual Hyprland child and retained source pidfd. The matching
Hyprland0.56.2-4 plugin sends original focus/lock facts with real per-packet kernel
credentials and exactly one owned focused Wayland socket-peer pidfd. The actual
`Observer` forwards its provider results into `run_with_messages_and_session`;
fixture diagnostics forward them unchanged. The lifecycle actor launches the
actual app generation as UID11010 and retains final current read authority. One
protected procfs and common PID/user/mount namespace are deliberately checked
inside the isolated guest. Production namespace/configuration containment remains
unqualified.

The chronological RED ran before this lane's Rust entrypoint existed. The normal
staged service initially denied, then manual root controls exposed actual diagnostic
Qt text with no established source. Conversely, original focus plus a separate
read grant could not reach that service after manual denial was restored. Those
are the two missing-composition assertions; they do not make the existing normal
service a production trusted-session implementation. The corrected fixture denies
unknown-source reads even after those root controls, then admits actual focused
app reads with the independent grant. Replaying that baseline later is regression
evidence, not a new test-first result.

The normal production screenshots were visually inspected: denied, local history,
revoked, restored and source-loss states are visible. The 320x240 captures show the
conversation, not the literal body. The separately labeled diagnostic ELF links
the actual production widget/controller/theme and observes literal body state.
It is not the normal production executable. Appearance is the existing fallback
palette in this joint selection; earlier original Omarchy theme qualification is
separate. Every selected compositor/source failure was observed as `TimedOut`;
these tests do not claim immediate EOF or a particular death-watch error path.

The original 100ms sample lease was never extended and no failed source was revived.
An actual locked graphics gap caused terminal expiry in both the initial lock
selection and a fresh attempt with an actual lock preparation before the first
adapter load/frame. Positive lock restoration is therefore an availability gate.
The stopped, unload and death checks use independent fresh epochs with no prior
locked-graphics expiry. Their passing results do not close that gate.

Qt image readback is suppressed while actually locked. The fixture qualifies
current actor/backend denial and later clearing after its explicit test unlock;
it does not establish immediate UI clearing, locked presentation or PAM unlock.
Previously released bytes, queued Qt callbacks and cached pixels cannot be
withdrawn by later source observation. No zero-publication race or secure output
claim follows. Genuine Omarchy Quickshell/PAM restoration, privileged Wayland
containment, production launch/source/configuration ownership, real resume/wake,
notifications and Pixel kernel/display/hardware remain separate gates.

All selected direct children have real wait results. Service-owned app/storage
children have retained pidfd death and process absence after service shutdown.
Some fixture cleanup uses bounded signals; this proves local ownership/reaping,
not remote cleanup or graceful behavior. Builds use immutable source selections
with 8 CPU/12 GiB quotas; independent VM jobs use existing dedicated clones/locks,
no NIC, read-only `snapshot=on` backing, four guest vCPUs and 6 CPU/8 GiB quotas.
No physical phone or unrelated workload was touched.
