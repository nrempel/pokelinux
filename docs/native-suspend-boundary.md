# Frozen V1 suspend Binder boundary

`native-suspend-boundary/` provides generated frozen V1 `ISystemSuspend` and `IWakeLock` Binder objects backed by the separate `native-suspend/` coordinator. An actual x86 SDK37 emulator run qualified original generated NDK proxies against the Rust dispatcher and the reverse Rust proxy against an original generated NDK V1 dispatcher. Kernel UID/PID/SID, one-way release, final reference destruction, transfer to a second native process and authority death all executed with SELinux enforcing. No host power interface, physical phone or factory vendor binary executed.

This is an isolated Binder object boundary. It is not an installed SystemSuspend replacement. The standard `android.system.suspend.ISystemSuspend/default` service was declared and already present. Attempting the dedicated `android.system.suspend.ISystemSuspend/pokelinux_test` registration returned `Security / Ok: SELinux denied for service.` The harness did not replace the stock default or weaken SELinux. A disposable instrumentation broker transports the exact V1 Binder objects instead. The frozen descriptors, scalar/string encoding, returned strong object, one-way transaction and version/hash methods use generated bindings from the exact public schemas; the discovery broker and lifecycle controls are explicitly synthetic.

Both frozen interfaces report version 1 and hash `082a58c2505b703702f34ab8abcb1d1b5e890be4`. The source pin is `android-17.0.0_r1`, matching the earlier selected factory NDK hash marker. The public compiler and shared NDK/helper headers are pinned in [the fetch manifest](../framework/suspendpeer/fetch-manifest.json). Downloaded original sources and generated trees remain ignored. `rsbinder` and its AIDL generator are locked to 0.12.0; the Rust source forbids unsafe code.

The native frontend records kernel-delivered caller UID, synchronous PID and requested SELinux context at acquisition. Its test admission policy allows UID 2000 and bounds names to 256 UTF-8 bytes; the SID is observed, not used as a production authorization profile. A native shell request reported its actual PID and `u:r:shell:s0`; an actual app-process call was rejected with a security exception and its different identity recorded. This test policy and name limit are deliberate native resource rules, not claims that the public Android service has those same checks. The frozen wake type is accepted and ignored as in the public implementation. Release authority follows possession of the Binder object, including transferred references, rather than the original acquisition PID.

Each returned Rust wake object owns a coordinator wake lease. Explicit release calls that lease once; destruction drops its remaining ownership. There is no daemon-wide strong map that prevents final object destruction. The observed lifetime cases were:

| Executed boundary | Result |
| --- | --- |
| Generated NDK V1 proxy to Rust dispatcher | Both descriptors/version/hash and returned remote object pass |
| One-way release while its server handler is held | The caller returns successfully while the counter remains one; receipt is separate from completion |
| Explicit release twice, followed by object destruction | Counter reaches zero once |
| Last remote Binder reference discarded | Native object destruction releases the coordinator lease |
| First client exits after transferring its object to the app broker | Wake remains held |
| Second native client obtains that object; broker discards its reference | Wake remains held by the second client |
| Second client is killed and explicitly reaped | Kernel reference cleanup destroys the native object and counter reaches zero |
| Rust V1 proxy to generated NDK V1 dispatcher | Metadata, native caller identity, clone/release and final destruction pass in the reverse direction |
| Controller token's native process is killed and reaped | Kernel death notification drops its owned native authority and permanently fences the coordinator |

The reverse-direction NDK endpoint is our synthetic native destruction ledger, not an Android suspend implementation. Its generated V1 dispatcher executes unchanged over Binder. The forward-direction endpoint uses the real native coordinator with private regular-file backend descriptors. Those files establish integration of Binder lifetime with native coordination; they do not perform kernel suspend.

The native authority retains its Binder death recipient, token and coordinator guard. The callback uses a weak state reference and generation check; losing the token drops the guard. The runtime then observed `AuthorityLost`, no armed authority, a disabled attempt and rejection of another arm. The native frontend has no automatic re-entry or service restart. The test supervisor explicitly created fresh server epochs with new isolated descriptor directories for client-cache experiments; this does not qualify recovery of an uncertain physical backend.

The original public `power.cpp` executes unchanged in two compiled clients, with and without `ENABLE_NO_LOCK_BINDER_TXN`. Logging/tracing adapters provide instrumentation only. Link-time adapters for `AServiceManager_isDeclared` and `AServiceManager_waitForService` provide the dedicated discovered V1 object and assert that the original client asks for its exact `/default` name. Actual wake RPCs, generated NDK proxies, C name map, static service cache and one-way release run in the original code. These discovery adapters are not proof of default registration or real manifest changes.

Both original client branches observed four behaviors: a controlled absent declaration is cached null even after declaration becomes available; repeated held names deduplicate RPCs; a held name still reports success after the real Rust service process dies, while a fresh name fails and release clears its entry despite transport failure; and an explicitly started replacement service does not make that cached client rediscover it. These results mean a libpower success return is insufficient evidence of a current native wake blocker after service death. They are original public client evidence, not execution or binary equivalence of the factory libpower ELF.

The broker stays alive across multiple native clients by using Android 17's `INSTR_FLAG_NO_RESTART = 8`. The installed original framework reflection oracle verified that value. Initial ordinary instrumentation starts restarted the broker and lost references; those bounded negative runs remain ignored and are not counted as the intended red. The intended runtime red then passed V1 metadata/identity and one-way receipt, and failed the explicit-release counter assertion. Adding the lease release made the unchanged scenario green. The full green run completed the table above and both client-cache branches. Native x86 build/format/clippy and ARM64 GNU compile/clippy passed. Actual Binder runtime evidence is x86 Android; ARM64 Binder, retained-vendor execution and physical-device behavior remain unqualified.

Reproduce with `tools/prepare-suspend-boundary.py`, `tools/build-native-suspend-boundary.sh build`, and `tools/build-suspend-boundary-peer.sh` in the prepared framework image. The dedicated `tools/suspend-boundary-suite.sh red|green` shares the exclusive framework lock while owning a separate package/container/network. It verifies installed framework transaction metadata and flags before tests, bounds clients/processes, checks PIDs against their own executable before killing, explicitly waits for them, and finally stops the app and emulator. A recorded historical fetch manifest is retained privately; later additions pinned already-used public toolchain files without changing runtime code or binary inputs.

[Structured provenance](evidence/native-suspend-boundary-provenance.json) pins the final owned source bundle, compiled public schemas, runtime artifacts and input identities. No original generated tree, upstream source tree, proprietary/raw audit material or credentials are published. No new REA session was needed for this source-backed work, and no existing coordinator or shared README/handoff source was changed.

The remaining deployment gates are standard default registration/VINTF and SELinux policy, a production permission and lifecycle authority, a supervised backend process for blocked Binder/sysfs calls, and an actual kernel/device profile for count rejection, `userspace-abort`, `pm_fs_abort` and suspend/resume. The test admission UID, instrumentation broker and synthetic control interface must not become production authorization or discovery. Frozen wire interoperability and real object death are now tested; installed authority and hardware suspend remain open.
